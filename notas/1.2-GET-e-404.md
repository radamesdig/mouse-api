Quando usamos o -i no curl, obtemos uma resposta com código de status HTTP, um cabeçalho (que mostra data, servidor, tamanho do conteúdo e tipo de conteúdo) e um corpo (que mostra a lista de objetos, no formato JSON). Se não usarmos o -i, obtemos a resposta sem o código de status HTTP e sem o cabeçalho.

Por outro lado, quando o cliente faz um pedido, ele passa as informações para o servidor, que vai fazer toda a validação e executar as funções das rotas, se necessário. O pedido também possui cabeçalho e corpo. E possui também o método a ser usado (POST, GET).

Caso o cliente utilize um endpoint com parâmetro de busca, após rodar a função da rota, podem ocorrer 3 situações:

1. O parâmetro informado for encontrado na lista de objetos da classe Pydantic e retornar o código de status 200, juntamente com o corpo. mostrando os atributos do objeto;

2. O parâmetro informado não for encontrado, mas ter o tipo válido já definido como parâmetro na função da rota e retornar o código de status 404, seguido de uma mensagem configurado no código;

3. O parâmetro informado não ter o tipo válido já definido como parâmetro na função da rota e retornar o código de status 422, de forma que a função da rota sequer será executada.

Caso o cliente utilize o endpoint para buscar a lista de objetos da classe Pydantic, se ainda não tiver nenhum objeto, retornará [] e com código de status 200, pois não houve nenhum erro na execução. 

Vale destacar que a função retornou algo, que é a lista. Se a função não fosse elaborada para retornar algo, a resposta seria null, e não [].

## Liga com

[classe pydantic](1.1-classe-pydantic.md): a validação feita pela classe Pydantic é importante para validar os dados e retornar o erro 422, se tiver incompatibilidade de tipo. Nesse caso, a função da rota nem será executada.
